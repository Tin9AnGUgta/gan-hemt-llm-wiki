# 執行反思

正式反思須根據實際執行紀錄撰寫，不能預先假設最常出錯的節點。

## 規劃階段已觀察的環境問題

- GitHub 連接器可讀帳號 Repo，不代表當前目錄已綁定本專案。
- 檔名年份與論文封面日期可能不同，書目不能直接由檔名產生。
- Windows 預設文字編碼曾使 PDF 抽取輸出出現亂碼；工具須明確使用 UTF-8。

這些是訪談／預檢觀察，不冒充五篇正式 ingest 的執行紀錄。正式執行後補入節點、失敗次數、檢查次數、修正與重跑證據；如無失敗，直接如實記錄。

## 第一次正式執行的公式解析問題

Graph 1.0 的 G1 使用文字抽取與公式編號候選，進入 G2:P01 後發現小數子編號（例如 3-4.1、3-6.3）未被原規則捕捉，且算式、編號與圖說的抽取順序不一定相鄰。來源沒有遺失公式，問題是抽取／配對方式不足。

已將 G2:P01 記錄為失敗，保留該次執行，再把檢查提前至 G1：支援小數子編號、列出公式候選所在的必要視覺核對頁，並保留「候選不等於完整」限制。以原論文實際出現的編號新增回歸測試，Graph 更新為 1.1 後建立新 run。此處不能推論其他節點較可靠，因為完整流程尚未走完。

## 第一輪私人筆記的連結檢查誤判

實際檢查時，初版連結規則把 LaTeX 中「方括號係數後接圓括號幾何比」誤判成 Markdown 連結，回報不存在的 `L/W` 檔案。這是檢查工具誤判，不是論文的錯誤，也不是實際斷鏈。

修正共用連結解析：先略過程式碼與數學區塊，再檢查真正的 Markdown 連結。以該次出現的數學結構與一個真實連結混合的情況新增回歸測試。檢查規則在 Wiki 產生後、進入人工審閱前即執行，避免把誤報留到 HTML 階段。

## 公開包實際執行揭露的測試缺口

初版測試涵蓋拒絕未登錄檔案，卻沒有走完「合法登錄 → 產生白名單 → 公開檢查」的成功路徑。實際 manifest 命令因重構後缺少輸出路徑變數而失敗，公開檢查也因此拒絕發布。沒有跳過檢查直接同步。

修正變數並新增完整成功路徑測試，還驗證白名單建立後改動檔案會被攔下。檢查提前到首次遠端同步之前；工程測試成功不再單獨作為「公開包可發布」的證明，必須另執行真實 manifest 與 check。

公開檢查亦曾把自身的 Unix 私人路徑偵測規則當成實際私人路徑。將規則前綴分段組合，避免字面自我匹配；新增「合法偵測程式碼可通過、真正路徑仍被拒絕」的回歸案例，沒有移除路徑保護。

## GitHub CI 揭露的跨平台換行問題

首次同步後，GitHub Linux CI 的單元測試通過，但公開雜湊檢查失敗。原因是 Windows 產生的部分 JSON／JSONL 使用 CRLF，而準備 API 上傳時的文字讀取將其正規化為 LF，導致遠端內容位元組與本機白名單不同。不是 PDF 被上傳，也不是將問題忽略後放行。

修正為公開文字一律 UTF-8／LF，加入 `.gitattributes`，JSON 寫入與公開事件匯出指定 LF；同步讀取原始 UTF-8 位元組，並檢查公開包不得有 CRLF。新增跨平台位元組測試，修正後重跑本機與遠端檢查。此經驗將「真正遠端檢查」保留為同步驗收，避免只以 Windows 本機通過宣稱跨環境可用。
